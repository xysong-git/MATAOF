# 优化机制说明：同一条语句，MATAOF 到底改变了什么

> 本文回答三个问题：对比 IoTDB 原生查询，**优化发生在哪里**、**哪些地方发生了改变**、
> **自适应到底适应了什么**。写实口径——包括当前实现"尚未传导到执行层"的部分。
> 最后更新：2026-10-26（measure_baseline=false 评估口径）

## 1. 两条执行链路对比

**原生（native）**：

```
SQL 语句 → IoTDB 服务器 → 解析 → 逻辑计划 → 分布式规划（IoTDB 内部自身的时间分区裁剪/谓词下推/chunk 元数据过滤）→ 物理执行 → 结果
```

**MATAOF（agent / llm 模式）**：

```
SQL 语句 → ① 查询分析（特征提取）→ ② 知识检索（历史经验）→ ③ 策略决策（确定性评分 + LLM 选择，合法性校验，确定性兜底）→ ④ 执行（equivalent_sql非空则用候选提供的 SQL，否则原查询）→ ⑤ 监控（事实采集）→ ⑥ 知识入库（执行反馈 → 评价表更新）→ ⑦ 追踪落盘
```

MATAOF 在"把 SQL 交给 IoTDB"**之前**插入了一个决策闭环；交给 IoTDB 之后的执行，
由 IoTDB 引擎按其自身能力完成。

## 2. 策略空间：三个维度、八种策略，各自声称影响什么

| 维度 | 策略 | 声称的影响 | SQL 可表达？ |
|---|---|---|---|
| time_pruning | full_scan | 不裁剪，按查询范围完整扫描（安全默认） | 否（执行层行为，SQL 不变） |
| time_pruning | partition_pruning | 依据时间边界跳过不相关分区 | 否（时间边界已在 WHERE 中） |
| time_pruning | chunk_level_filtering | 时间过滤下沉到 chunk 级 | 否（执行层能力，无对应语法） |
| filter_order | time_first | 优先评估时间过滤（时序库按时间物理组织） | **是**（WHERE 谓词重排 = 等价 SQL） |
| filter_order | device_tag_first | 优先评估设备/标签过滤 | **是**（同上） |
| aggregation_placement | final_level_aggregation | 聚合在最终层（数据库默认，安全默认） | 否（执行层概念） |
| aggregation_placement | intermediate_level_aggregation | 聚合在中间层（分组后、归并前） | 否（无对应语法） |
| aggregation_placement | scan_level_aggregation | 聚合下推到扫描层 | 否（执行层能力） |

**关键事实**：8 个策略中只有 filter_order 的两个是"SQL 可表达"的；其余 6 个是**执行层概念**——它们的生效需要执行引擎具备对应能力并把策略传递下去。

## 3. 当前执行层的现实（诚实说明）

执行层（`executors/iotdb.py`）的逻辑：

```
sql = strategy.equivalent_sql
if not sql:
    sql = 原查询
执行 sql（IoTDB 引擎按自身能力执行）
```

当前实验配置下：

- 候选策略集合为空配置 → 目录全集 → **所有候选的 equivalent_sql 均为 None**；
- strategy_parameters（如 time_pruning 的 {start_time, end_time}）**只记录在 trace
  中，不被执行层消费**。

因此：**当前实验的执行层面没有发生任何改变——发给 IoTDB 的 SQL 与原生查询完全相同，执行路径、执行引擎行为完全一致**。策略选择是"声明"（strategy_id +参数记录），尚未传导到执行。此前批次汇总里的效果分布（improved/degraded）来自同一条 SQL 的两次执行抖动与缓存状态差异（旧口径下的配对双执行），**不是策略的执行效果**——去掉双执行后，跨轮对比（native vs mataof）在执行延迟上预期无显著差异。

设计意图上，执行级改写由**候选提供方（外部系统）**给出（`equivalent_sql`字段），决策只选择、不生成 SQL——这是"混合模型"的既定设计；当前没有候选提供方，所以执行级改写是空白的。

## 4. 自适应到底适应了什么（当前真实存在的部分）

自适应是**决策层的闭环**，它真实存在并随运行演进：

```
查询特征（类型/时间档位/聚合结构/过滤模式）
数据库状态（规模档位/设备规模）        ──→  策略决策（三维度 × 8 策略中选择）
系统状态（负载档位）
历史执行反馈（评价表：各策略在该查询类型下的
  成功率/延迟分布/失败模式）             ←──  执行反馈逐条入库、按签名聚合
LLM 经验摘要（评价表的量化投影）
```

- **适应的对象 = 策略选择本身**：同样的查询类型，随着经验积累，系统对
  "该类型查询选哪个策略"的判断随真实执行反馈动态修正（成功率高的策略获得
  更高先验；失败经验计入失败统计，不会计为成功）；
- 学习闭环真实运转：执行事实 append-only 入库 → 评价表/签名聚合更新 →
  影响后续检索证据与决策（确定性先验 + LLM 经验摘要）；
- 跨数据集迁移成立：经验键按查询类型（非数据集）组织，新数据集的第一条
  查询即可命中历史同类经验。

**尚未成立的部分**：选择的产物（策略声明）当前没有改变执行路径，所以
"自适应"还停在"选择器"层面——选对了，但执行层没听。

## 5. 通往"真实执行级优化"的路径

> **已实施（2026-10-26，D11）**：策略空间按实测杠杆重设计——目录替换为
> alignment（time_aligned / align_by_device，SQL 级：`ALIGN BY DEVICE` 子句）
> 与 fetch_size（fetch_default / fetch_large，执行参数级：执行层多会话消费）；
> 新增候选提供方（`optimization_decision/provider.py`）按查询生成等价 SQL/参数。
> 实测背书（scripts/bench_sql_levers.py）：ALIGN 15~25×（宽设备扫描）、
> fetch_size ~15-20%；被剔除的：谓词重排（优化器归一化≈0）、查询拆分（更慢）、
> 时间收紧（无用）、窗口形式（SESSION/滑窗——**语义不等价**，不能作为同查询改写）、
> LAST（语料已是 LAST 写法）。当前系统**真实改变执行路径**：多设备查询的选择
> 决定是否带 ALIGN BY DEVICE，批次大小决定会话 fetch_size。

进一步路径：

1. **候选提供方扩展**：按库方言为更多数据库无关的杠杆生成 SQL（换时序库只换
   适配器——alignment/fetch_size 概念在各主流时序库均有对应）；
2. **D7 策略追踪（oracle）**：EXPLAIN/执行统计验证引擎是否按所选策略执行；
3. 语义等价校验器：候选提供方扩展时配套（校验不过回退原查询）。

## 6. 与实验数据、论文口径的关系

- 旧数据（配对双执行口径）中的 improved/degraded 分布是双执行噪声 +
  缓存效应，**不能作为策略执行效果的证据**；新口径（measure_baseline=false，
  baseline 由 native 轮承担，每批清缓存）下，native 与 mataof 的执行延迟
  预期同分布——直到路径 1/2 落地前，论文应如实呈现"决策闭环的开销与
  执行层改造前的空窗"；
- 论文的诚实框架建议：把"优化开销 vs 执行节省"的 break-even 分析与
  执行级改造（候选提供方）绑定——改造前展示决策层闭环本身（自适应学习
  机制），改造后展示端到端收益；
- 效果评估的干净口径 = 跨轮对比（native 轮 vs mataof 轮，同缓存清理协议）
  的每语句执行耗时差异。
