# Agent 协同开销优化方案

日期：2026-10-09（A1/B1/B2/B5 已实施，B3/B4 待定）
问题：110 条查询总用时 919s（8.35s/条），而真实查询延迟仅 avg 13.29ms——**99.8% 的
时间花在 Agent 推理与交互上**。

**实施状态（2026-10-09 全部完成）**：
- ✅ A1：`sample_rate=10` 已写入全部 llm 配置文件（每 10 条启用一次完整 LLM 增强）；
- ✅ B1：监控解读 + KM 经验总结合并为一次调用（每条 LLM 调用 4→3 次，-25%），
  数字级校验在合并路径同样生效（测试固化）；
- ✅ B2：`--workers N` 查询级并行（runner 线程池 + 知识库/执行层线程安全 + 保序）；
- ✅ B5：知识库批量落盘（`knowledge_save_interval=20` 已写入实验配置）+ 紧凑序列化
  + flush（批次结束强制持久化）；
- ✅ B3：LLM 输出缓存（`CachedLLMClient`，prompt 哈希+模型名键、持久化写穿、
  线程安全、容量上限；`cache_file` 已写入 llm 配置）——同查询集第二轮起
  LLM 开销趋零；缓存只存原始响应，各 Agent 的解析/防编造校验照常执行；
- ✅ B4：异步增强模式（`async_enhance: true` 已写入 llm 配置）：确定性链路
  **零 LLM 调用**（~50ms/条）同步完成落盘，后台线程补写 QA 摘要/决策解读/
  合并解读到 trace（含文件回写）；批次结束自动排空；`preference_bonus` 开启时
  强制回退同步；异步经验总结只补写 trace、**不写入知识库记录**（append-only 原则）。
- 最终效果：主链路回到确定性量级（全量 6.6 万条约 1~2 小时），LLM 增强产物
  由后台补齐；重复轮次叠加 B3 缓存后 LLM 开销趋零。

## 一、实测开销分解（证据）

| 阶段 | 单条耗时 | 依据 |
|---|---|---|
| 4 次串行 LLM 调用（QA 摘要 + 决策解读 + 监控复述 + KM 经验总结） | **≈8.38s** | `data/llm_log.jsonl` 6184 次调用实测：平均 2295ms、P50 2095ms；4 × 2.1s ≈ 8.38s，与实测 8.35s/条几乎完全吻合 |
| 确定性链路（分析/检索/决策评分/监控判断/入库） | ≈50ms | 早前实测（库 1100 条时检索 38ms 等） |
| 真实执行（baseline + 策略双执行） | ≈28ms | 本批次 avg 13.29 + baseline 15.02 |

**结论：LLM 调用是唯一瓶颈，占 ~99.8%**。确定性链路与真实执行都不是问题。
（注：开题报告 2.3.1 把"低开销协同"列为关键问题——本优化正是研究内容本身，
实验结果可写入论文作为协同开销控制的验证。）

## 二、方案（按实施成本从低到高）

### A 档：配置级（零代码，立即生效）

**A1. LLM 采样降频**（已有能力，改一个数字）
- `llm.sample_rate` 从 1 改为 10~20：每 10 条查询启用一次完整 LLM 增强，
  其余走确定性快路径（决策逻辑不变，仅缺 LLM 附加解读）。
- 预估：110 条 ≈ 11×8.4s + 99×0.05s ≈ **97s**（9× 提升）。
- 适用：实验目的是策略效果对比、不需要逐条 LLM 增强时。

### B 档：代码级优化（按收益排序）

**B1. LLM 调用合并：4 次 → 3 次**（改动小，-25%）
- 监控复述与 KM 经验总结发生在同一时刻、输入几乎相同（监控输出+执行结果）——
  合并为一次调用，两个 Agent 分别取各自字段。
- 预估：8.38s → **6.3s/条**（110 条 919s → ~690s）。
- 各 Agent 的 llm_enhance 保留独立调用能力，仅在 runner 链路合并。

**B2. 查询级并行：`--workers N`**（吞吐提升 ~3×）
- runner 线程池并行处理查询；vLLM 自带 continuous batching，并发请求总吞吐
  近似线性提升（单请求延迟会上升，总时间下降）。
- 需要配套：MemoryStore 加锁（append-only 并发安全）、保存序列化、
  LLM 客户端线程安全确认（urllib 无状态，安全）。
- 预估：workers=4 时 110 条 ≈ **280~350s**（3× 提升）。

**B3. LLM 输出缓存**（二次运行 ~90×，适合你的场景）
- 查询集同质（q1~q11 模板变体），语义摘要/解读高度重复——按"任务类型+特征键+
  prompt 哈希"缓存 LLM 结果（实验内有效，可配置）。
- 第一轮仍是全量 LLM 开销；**第二轮起几乎零 LLM 开销**（命中 ≈50ms/条）。
- 注意：缓存会固定 LLM 输出，做 LLM 消融实验时按组关闭缓存保证公平。

**B4. 异步增强模式（可选）**（决策链路回到 43ms 量级）
- 决策/执行/监控/入库同步完成并落盘（确定性，43ms/条）；LLM 解读改由后台队列
  异步批量生成、完成后补写 trace 的 llm_analysis 字段。
- 开启 `preference_bonus` 时自动回退同步模式（LLM 参与评分必须同步）。
- 预估：主链路 ≈**50ms/条**（110 条 ≈ 10s），LLM 产物在后台补齐。

**B5. 确定性侧微优化**（合计 ~50-200ms/条，库大后有意义）
- 证据相似度只算一次：KM 输出携带 similarity，决策端跳过重算（契约小改）；
- 知识库批量落盘（每 N 条或退出时保存，可配置 save_interval；默认保持每次保存）；
- trace/知识库紧凑序列化（去掉 indent）。

### C 档：模型侧（你自行权衡）
- 更小/量化模型、vLLM 调参（更高的 gpu-memory-utilization、prefix caching
  对同质 prompt 收益明显——我们的系统提示词重复发送，vLLM prefix cache 可直接
  降低每次推理时间）。

## 三、量化对比总表（110 条）

| 方案 | 单条耗时 | 110 条总用时 | 提升 |
|---|---|---|---|
| 现状 | 8.35s | 919s | — |
| A1 sample_rate=10 | ~0.9s | ~97s | 9× |
| B1 合并调用 | ~6.3s | ~690s | 1.3× |
| B2 workers=4 | ~8.4s（排队变长） | ~300s | 3× |
| B1+B2 | — | ~230s | 4× |
| B3 缓存（第二轮起） | ~0.05s | ~10s | ~90× |
| B4 异步增强 | ~0.05s（主链路） | ~10s + 后台补齐 | ~90× |

## 四、推荐实施路线

1. **今天**：把 `sample_rate` 调到 10（A1），立即恢复可用吞吐；
2. **短期（约 1 天）**：B1 合并 + B2 workers + B5 微优化 → 全量 LLM 下 4~5× 吞吐，
   且逐条增强产物完整；
3. **中期**：B3 缓存（多轮实验场景收益最大）或 B4 异步（按你是否需要同步 LLM 参与
   决策而定，二者选一）；
4. **论文素材**：无论选哪条路线，把"优化前后协同开销对比"做成一张表/图——
   正好呼应开题报告 2.3.1 的"低开销协同"关键问题。

## 五、风险与注意事项

- B2 并行要求知识库线程安全（加锁）+ 结果文件唯一性（run_id 机制已保证）；
  先补并发测试再放开；
- B3/B4 会改变"每条查询都有同步 LLM 输出"的语义，实验设计时需分组标注；
- B4 异步模式下 LLM 增强与执行脱钩，`preference_bonus` 实验必须用同步模式；
- 所有优化不改变决策逻辑本身——只改变"LLM 增强何时/如何产生"，策略效果实验
  的可比性不受影响（确定性路径不变）。
