## 二、遇到的问题与解决方案（按类别）

### 2.1 正确性与可靠性

| # | 问题 | 根因 | 解决方案 |
|---|---|---|---|
| 1 | 查询集文件执行失败（SQL 解析报错） | `--` 注释行被当作 SQL 发给 IoTDB | `split_sql_statements` 统一去注释 |
| 2 | 结果文件同名覆盖，多轮运行互相覆盖 | 自动 query_id 每文件重新编号 | run_id 时戳前缀 + 防冲突后缀 + source 字段 |
| 3 | `SELECT last` 查询（q8）与 BOOLEAN 传感器报错 | 数据真实特性 / 类型不匹配 | 如实记录失败经验（系统行为正确，非 bug） |
| 4 | 通配符 `--file q*.sql` 后 10 条查询失败 | bash 展开为多参数，`--file` 只接第一个，其余文件路径被当 SQL 执行 | `--file` 支持多值；位置参数像路径时明确报错 |
| 5 | 路径列引用丢失测点名（`root.sg.d.s1` 只取到 `root.sg.d`） | sqlglot 将路径列解析为 Dot 链 | `full_reference` 沿 Dot 链重建完整路径 |
| 6 | 并发写盘 FileNotFoundError | 多线程写同一 tmp 路径竞态 | 唯一 tmp 名（pid+线程）+ 写锁 + 原子 replace |
| 7 | 等价性 bug ×4（向量化实现阶段） | 单方缺失误写 0.5 / 读错字段键 / 增量 vstack 宽度 / 函数字典外名字误判空集 | 等价性测试逐字段对照修复（测试先行的价值） |

### 2.2 LLM 接入

| # | 问题 | 根因 | 解决方案 |
|---|---|---|---|
| 8 | 本地 vLLM 调用返回 502 | 系统 `http_proxy` 环境变量使请求绕经 clash 代理 | 本地地址自动绕过代理直连 |
| 9 | Qwen3 输出进入 `<think>` 块、响应慢 | Qwen3 默认 thinking 模式 | `chat_template_kwargs: {enable_thinking: false}` |
| 10 | 监控复述被数字校验误杀（"CPU 42%"） | LLM 把 0.42 写为 42% 被严格校验拒绝 | 校验允许 ×100/÷100 单位换算（量级校验仍拒绝编造） |
| 11 | 919s/110 条，99.8% 时间在 LLM | 每条串行 4 次 LLM 调用（P50 2.1s） | A1 采样 + B1 合并（4→3）+ B4 异步化 + B3 缓存 |

### 2.3 性能（"越跑越慢"系列，最终全部定位并解决）

| # | 问题 | 根因 | 解决方案 |
|---|---|---|---|
| 12 | 异步模式每个文件后"卡住"5 分钟 | 逐文件排空异步补写队列 | 排空推迟到轮末（drain_llm=False）+ 补写尊重 sample_rate |
| 13 | 主流程结束后等待 LLM 补写 | 默认等待排空 | `async_drain_timeout=0` 默认不等待，未完成如实标记 |
| 14 | workers=4 反而更慢 | GIL：异步/无 LLM 主链路为 CPU 密集，多线程串行化+切换损耗 | 异步模式自动降级 workers=1；并行仅在同步 LLM 模式有效（实测 1.75×） |
| 15 | 29k 库单条 2.2s | `statistics()` 每查询两次 O(N) 全表扫描 + 40MB 落盘在锁内 + 检索全库扫描 | statistics 增量化（O(1)）、锁内快照+锁外写盘、检索免 view、汇总单遍 |
| 16 | 51k 库检索 516ms/条 | 全库相似度扫描的 Python 后处理随库线性增长 | numpy 向量化扫描（29k 库 619→273ms；语义与逐条完全一致，测试保证） |
| 17 | 22k 全量 4.6 小时（760ms/条） | 检索 68% + 落盘 13%（70MB 每 10 条一次） | save_interval 20→500（落盘均摊 ~100→~4ms/条）+ 每轮独立知识库建议 |

### 2.4 设计修正与语义澄清

| # | 问题 | 结论/方案 |
|---|---|---|
| 18 | 决策输出"应该是什么"的疑问 | 混合模型：策略标识 + 候选提供方的等价 SQL + 执行级参数（决策只选择、不生成 SQL） |
| 19 | baseline 机制疑问 | 逐条配对双执行（同 Session 紧邻，公平对照）≠ native 模式（轮次级对照组） |
| 20 | 批次/总体汇总重叠 | 批次=每文件独立统计；本轮总体=调用级；轮次汇总=run_id 隔离跨文件 |
| 21 | P50/P95/P99 何时生成 | 分位数是多样本统计：批次结束/最终汇总时对真实样本计算，单次执行不编造 |
| 22 | 文件顺序"像随机" | bash 字典序展开（q1,q10,q11,q2）→ `sort -V` 版本排序；取样一直是文件内随机（种子可复现） |

## 三、目前已经做了什么（能力清单）

**四个 Agent（全部确定性核心 + LLM 混合增强）**
- ① Query Analysis：sqlglot 解析 + 六类特征 + 29 维特征向量 + 语义摘要/类型提示/标签判别
- ③ Optimization Decision：有界策略空间（8 策略/三维度）、五因子评分（base/context/history/评价表先验/system/LLM 加分）、三级风险门控、安全回退、混合输出（equivalent_sql）
- ⑤ Execution Monitoring：事实采集、baseline 对比、效果判断、9 类异常、数字级防虚构
- ④ Knowledge Memory：append-only 存储、三层相似匹配、成功/失败模式、策略评价表（D1 动态权重）、top-K 证据截断

**基础设施**
- 共享 LLM 层（OpenAI 兼容/本地 HTTP 双后端、缓存、调用日志、失败兜底）
- 执行层抽象（Null/File/IoTDB 执行器；真实指标采集含 CPU/内存平均+峰值）
- 正式入口：`mataof run/retrieve/stats` CLI、PipelineRunner、tqdm 进度
- 四模式实验脚本（native/fixed/agent/llm）+ 每文件取样（seq/random+种子）
- 配置生成脚本（消除配置漂移）、批次/轮次汇总（指标与排版统一）
- 性能体系：采样/合并/异步/缓存/向量化扫描/增量统计/锁外落盘

**验证体系**
- **243 个自动化测试**（含真实 IoTDB 集成、向量化等价性、并发安全、防虚构等）
- 真实数据：IoTDB 2.0.6 三规模数据集（root.dbs/dbm/dbl.g_0）
- 文档 10+ 份（Agent 规格、流程说明、运行手册、对比报告、差异分析、冗余审查、性能方案、本总结）

## 五、关键经验教训

1. **测试先行救场**：向量化实现的 4 个等价性 bug 全部被逐字段测试抓住；"无虚构"原则
   靠数字级校验落地
2. **先测量后优化**：919s、4.6 小时、workers 反向加速——每次都用实测数据定位根因
   （数据库 6ms 无罪、GIL 反效果、70MB 落盘），避免猜测式调优
3. **演进中的设计失效**：B2 并行被 B4 异步化后失去前提（默认路径自动降级）；知识库
   append-only 的价值与规模成本需要权衡（每轮独立库）
4. **实验可复现贯穿始终**：run_id/种子/采样说明/证据快照/append-only——任何一次运行
   都可事后审计
